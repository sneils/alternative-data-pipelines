Inside a QR code

Reed-Solomon in 60 seconds

  • our data: two numbers -> drawn as two points
  • yup -> that's a line
  • transmit any five points from that line -> the three extras are parity
  • lose any three -> still the same line
  • Reed-Solomon is this trick over bytes
The only math slide - keep it at picture level: k points of data, n on the wire, ANY k rebuild everything. If someone asks afterwards: the real thing runs over GF(256) so bytes stay bytes - same picture. Act 3 calls back to this: L/M/Q/H is just "how many extra points", erasures-vs-errors is the fine print.

Show the wire

v1|8a3fc2d1|17|128|audience.jpg|image/jpeg|9c2e41d7|iVBORw0KGgoAAAANS…

  1. v1 - version tag - which frame format is this?
  2. 8a3fc2d1 - file id - identifies a unique transfer
  3. 17 - sequence - which piece...
  4. 128 - total - ...of how many. Together: enough to know when you're done.
  5. audience.jpg - name - of the file
  6. image/jpeg - type - a mime.
  7. 9c2e41d7 - CRC-32 of the piece - another layer of security
  8. iVBORw0KGgoAAAANS... - a chunk of content - 400 bytes -> 536 chars including the base64 tax

Erasures vs errors

  • erasures: known-missing - r parity fixes r losses
  • errors: unknown-position - locating costs as much as fixing → r parity fixes r/2
  • decode is all-or-nothing -> a frame arrives perfect or not at all

Stop sending chunks.
Send chunks of chunks.

  • each frame = XOR of a random subset of chunks
  • catch any frames, in any order -> decode
  • no feedback channel required

A hand-made decoder

Real peeling, curated input: 5 chunks, 6 frames. Press → to advance each beat. Start: one degree-1 frame (f0) is dashed - that's the seed. Each press fires the highlighted frame (its last unknown turns green) and peels it out everywhere, which lights up the next ready frame - the cascade. Last beat: f5 was redundant → that's the overhead ε you just saw in the chart.

Why mostly 1s and 2s

  • degree 1 -> a few singles to seed
  • degree 2 -> the bulk: cheapest frames that still bring value
  • the spike -> some big ones that mop up the stragglers
Real robust-soliton PMF from lib/protocol.js (K=64). Too many degree-1s → wasteful duplicates; too few → the decoder starves with nothing to peel. The far orange spike is the robust term: without it, the last chunk or two almost never gets covered - that spike is exactly what stops the naive-style stall.

Design for missing data

  • you never (ok sometimes) receive "all the frames": voluntary, partial, biased samples
  • build for incompleteness instead of hoping for completeness
  • (hope is not a strategy, ~Yenia, 2026)
